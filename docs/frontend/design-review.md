# Проверка и перенос дизайнерского прототипа

## Полученный комплект

Полная дизайнерская версия содержала 64 файла TypeScript/TSX, все локальные импорты разрешались. Она включала оболочку, карточки вузов/проектов, административные экраны, дополнительные стили, брендовые ресурсы и проверки прототипа. После переноса отдельный каталог исходников удалён. Его README, Dockerfile, менеджер пакетов и режим preview относились к прототипу и не задавали правила запуска CRM.

## Наблюдения

- Дизайнерская модель `crm-model.ts` отличается от серверного контракта: фиксированные строковые stage IDs, поля city/region/nextAction, массивы строк вместо документов и комментариев. Нельзя заменить fixtures ответом API без адаптации предметной модели.
- Действия прототипа изменяют React state и сбрасываются при обновлении. В production все изменения подтверждает сервер; после мутаций обновляется TanStack Query cache.
- Прототип скрывает административные инструменты флагом preview. В CRM видимость интерфейса определяется действующими ключами прав; сервер остаётся источником авторизации.
- KPI и графики нельзя считать по одной странице реестра. Общие показатели берутся из серверных агрегатов; локальные сводки явно обозначают свою выборку.
- Кнопки `__case-files`, переключатели искусственных ошибок, деморолей, оформления/шрифтов и локальные выгрузки не переходят в production.
- Город, регион и эмблема вуза отсутствуют в согласованной серверной модели. Синтетические значения и привязку логотипов по названию не переносим.
- Вход не хранит токены в localStorage/sessionStorage. Конфигурация публичного клиента выдаётся сервером; единый `.env` и правила Docker сохраняются.
- Проверки прототипа полезны для доступности и адаптивности, но проверяют demo fixtures и локальные действия. Production проверяется отдельно с API и корпоративным входом.

## Границы реализации

Схема БД не меняется. Дополняются публичная конфигурация входа и серверные фильтры списка проектов. FSD разделяет общие элементы, предметные API/типы, операции, составные блоки и страницы. Существующие изменения OpenAPI сохраняются; контракты клиента сверяются с актуальным сервером.

Реальный обмен с LMS/сайтом ожидает внешних контрактов. Создание аккаунтов/приглашений из CRM, генерация договоров и импорт расширенных файлов кейса не определены текущими API и требованиями; их нельзя подменять локальной имитацией.
