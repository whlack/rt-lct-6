# Production-клиент CRM

## Структура и поток данных

Клиент — React + Vite + TypeScript, TanStack Query, Tailwind CSS. Слои FSD:

- `app/` — провайдеры, маршруты, обработка непредвиденных ошибок, стили и брендовые токены.
- `pages/` — композиция экранов без прямого доступа к БД или внешним системам.
- `widgets/` — оболочка, таблица проектов, история, очередь заданий, статистика.
- `features/` — корпоративная сессия, поиск, создание проекта, контакты, назначения, поля, workflow, документы, комментарии и экспорт проекта.
- `entities/` — типы и публичные API предметных сущностей. Серверное состояние принадлежит TanStack Query; контекст очереди хранит только ссылки на задания.
- `shared/` — HTTP-транспорт, контекст пользователя, элементы интерфейса и общие функции.

Срезы импортируются через публичные `index.ts`/`index.tsx`. Составные блоки одного слоя передаются через композицию: оболочка получает очередь от `app`, поиск находится в `features`.

Экран → предметный API → same-origin `/api` → контроллер NestJS → сервис → репозиторий → PostgreSQL. Импорт и выгрузки выполняет worker; клиент наблюдает `GET /api/jobs/:id` и скачивает результат через защищённый API. Прямых обращений к S3, LMS, сайту или административному API Keycloak в браузере нет.

## Сессия и права

Публичный `GET /api/config` выдаёт только URL, realm и client ID. Keycloak JS инициализируется один раз до маршрутизатора; Authorization Code + PKCE S256 обрабатывает callback. Для запросов обновляется токен; access/refresh tokens не сохраняются в localStorage, sessionStorage или заданиях. Сохраняется только тема `crm-theme`.

`GET /api/me` определяет имя, роль, разрешённые операции и видимость. Интерфейс скрывает недоступные действия и защищает прямые маршруты; сервер проверяет каждую операцию самостоятельно. Клиент обновляет профиль раз в минуту, сбрасывает данные при смене прав/видимости и очищает кэш при завершении сессии. Отчёты и статистика имеют независимые права.

Запросы включают фильтры и страницу в cache key. Мутации не повторяются автоматически; связанные ключи инвалидируются после ответа, в том числе после конфликта состояния. Очередь опрашивает активное задание до конечного состояния; ID последнего задания можно восстановить из URL. Полный отчёт проекта создаётся без фильтров периода.

## Дизайн и границы

Используется выбранное фирменное оформление со светлой и тёмной темами. Брендовые ресурсы и шрифты находятся в `frontend/public/`; происхождение описано в [SOURCES.md](../../frontend/public/brand/SOURCES.md). Демоданные, preview, переключение ролей/оформлений/шрифтов, искусственные ошибки и локальные файловые операции отсутствуют. Дизайнерский исходник не входит в Docker build context.

Сопоставление всех экранов и отличия предметной модели находятся в [анализе дизайна](./design-review.md). Клиент использует текущий проектный workflow и реальные поля сервера. Расширенные профили импорта, генерация договоров, приглашения сотрудников и география вузов требуют отдельных требований/контрактов.

## Docker и статические ресурсы

Оба приложения и их зависимости запускаются через Docker согласно [README](../../README.md). Frontend production target собирает Vite и отдаёт SPA через nginx. `API_UPSTREAM` из `.env` передаётся через Compose в frontend: Vite использует его для dev proxy, nginx подставляет в шаблон при запуске и направляет `/api/` в backend. Внешний nginx завершает TLS и может направлять все запросы CRM во frontend на порт 80. Любой глубокий маршрут возвращает `index.html`. Параметры входа задаются сервером во время запуска, поэтому клиентский образ одинаков для окружений. `VITE_*` не используется для runtime-конфигурации: эти значения встраиваются в JavaScript при сборке. `FRONTEND_ORIGIN` — внешний origin браузера, `API_UPSTREAM` — внутренний адрес API; они имеют разные назначения.

Согласованный шаблон импорта хранится единожды в `docs/templates/catalog-import.xlsx`. Vite отдаёт его локально и включает в production по адресу `/templates/catalog-import.xlsx`; Docker копирует этот источник перед сборкой.

## Проверка

Обычные проверки workspace: `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check`. Контейнеры собираются из зафиксированного lockfile.

`./scripts/frontend-check.sh --local` строит production API, worker, tooling и frontend, запускает одноразовый стек с отдельными томами и случайными портами, применяет миграции, выполняет серверные интеграционные тесты и браузерные сценарии с настоящим OIDC-входом. Рабочие `.env`, Compose и данные пользователя не меняются. Стек удаляется после завершения; артефакты сохраняются в игнорируемой `.artifacts/rt-crm-frontend-*`.

Браузерные проверки покрывают контакты, каталоги, создание проекта, nullable-поля, назначения, настройку и фиксацию workflow, обязательные файлы, комментарии/ответы, закрытие и историю, четыре формата отчётов, статистику, импорт с отдельным применением, поиск, глубокие маршруты, мобильную ширину, права и видимость КАМ, выход. Проверки производительности и формальная приёмка из [ROADMAP](../../ROADMAP.md) выполняются отдельно.
