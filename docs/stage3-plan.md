# Этап 3 — каркас серверных интеграций LMS и сайта

## Результат и согласованные границы

Реализовать API состояния и ручного запуска, историю заданий PostgreSQL, очередь BullMQ, расписание, обработку отказов и наблюдаемость в существующем worker. Фронтенд исключён.

Контракты источников отсутствуют. LMS и сайт имеют `NOT_IMPLEMENTED`; реальные запросы, маппинг и изменения предметных данных не реализуются. Каркас не означает завершения интеграций или полной приёмки MVP.

Требования будущего подключения: источники передают данные в CRM, новые сущности создаются автоматически при наличии обязательных данных; очередное внешнее изменение перезаписывает ручное значение. КАМ поступает из источника и однозначно сопоставляется с Keycloak. Без него проект не создаётся. Конкретные поля, сопоставление и политика удаления остаются вне каркаса.

## Модули и API

`integration-sync` содержит контроллер, сервис, репозиторий, реестр и диспетчер. Адаптеры размещаются в слое интеграций. Публичный интерфейс модуля используется существующим worker; `/api/jobs` остаётся контрактом выгрузок и импорта.

| Маршрут                                  | Поведение                                                                                  | Право                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------- |
| `GET /api/integrations`                  | Два источника, готовность, причина, интервал, следующее время и последнее задание          | `integrations.manage` |
| `POST /api/integrations/:source/sync`    | `409 SOURCE_NOT_IMPLEMENTED` без записи задания; для реализованного адаптера `202 {runId}` | `integrations.sync`   |
| `GET /api/integrations/:source/runs`     | История, page/pageSize, 25 по умолчанию, максимум 100                                      | `integrations.manage` |
| `GET /api/integrations/:source/runs/:id` | Состояние, ID инициатора, времена, попытки и безопасный код ошибки                         | `integrations.manage` |

Источники: `LMS`, `WEBSITE`. Неизвестный источник/задание — 404; неверные параметры — 400. История сортируется по созданию и ID по убыванию; не выдаёт профили, аренду или внешние данные. Начальный уровень обоих прав — 20. Seed сохраняет администраторские изменения.

## Состояние и выполнение

Добавить `IntegrationSyncRun`: UUID, источник, MANUAL/SCHEDULED, необязательный инициатор, QUEUED/RUNNING/SUCCEEDED/FAILED, времена, число попыток, следующий срок попытки, код ошибки, execution ID, срок аренды, время доставки в Redis и время планового запуска. Внешние ID, курсоры и JSON не хранить.

Частичный уникальный индекс допускает одно активное задание на источник. Уникальность источника и планового времени предотвращает повторное срабатывание расписания. Повторный ручной запуск — `409 SYNC_ALREADY_ACTIVE`; занятый источник расписание пропускает.

Очередь `crm-sync`, параллельность по умолчанию 1. БД подтверждает результат; диспетчер каждые 5 секунд восстанавливает доставку с постоянным `sync-<UUID>`. Аренда 30 секунд продлевается каждые 5 секунд. Условная запись по execution ID и действующей аренде не позволяет устаревшему исполнителю изменить результат. Завершённые задания повторно не выполняются.

Расписание проверяется каждые 30 секунд в worker. Интервал каждого источника по умолчанию 3600 секунд, отсчитывается от UTC Unix epoch. Обрабатывается только текущий интервал, пропущенные не накапливаются. Нереализованные источники пропускаются; `nextRunAt = null`.

Временные ошибки допускают три попытки с задержками 10/20 секунд; подтверждённый Retry-After увеличивает задержку. Срок повторной попытки хранится в БД, BullMQ доставляет одну попытку. Ошибки данных, доступа и отсутствующей реализации окончательные. Перед ручным заданием worker заново проверяет текущие роли автора через Keycloak и право `integrations.sync`; токены не сохраняются. Сбой на последней попытке после истечения аренды завершается `RETRY_EXHAUSTED`.

Адаптер получает ID задания и AbortSignal; потеря аренды отменяет выполнение. Будущий адаптер обязан обеспечить идемпотентность прикладных изменений. Тестовый адаптер существует только в проверках.

## Эксплуатация

Настройки `.env`: `LMS_SYNC_INTERVAL_SECONDS`, `WEBSITE_SYNC_INTERVAL_SECONDS`, `SYNC_CONCURRENCY`, `SYNC_RUN_RETENTION_DAYS` (90). Очистка удаляет только завершённые задания; срок является техническим значением до организационного согласования. Новых контейнеров нет; обновляется только Compose-пример.

Worker при остановке прекращает приём заданий и ждёт текущее выполнение. Отключённые источники не влияют на готовность API. Метрики показывают очередь, ожидание, длительность, ошибки, повторы и очистку. Логи содержат ID и код результата, без токенов, профилей и ответов источников.

## Проверки и поставка

Проверить недоступные источники и отсутствие заданий, права и DTO, расписание, повторный seed, стабильную историю и безопасную проекцию. Через тестовый адаптер проверить успех, временную/окончательную ошибку, исчерпание попыток, потерю права, сбой Redis, восстановление доставки, повторы, конкурирующие запуски, истечение аренды, рестарт worker и очистку без изменения предметных данных.

Проверки PostgreSQL/Redis и миграций выполнять в изолированных Docker-контейнерах. Перед push и MR: все обычные тесты, интеграционные проверки, типы, линтинг, форматирование, сборки backend и затронутых Docker-образов. Frontend не собирается. Обновить Swagger, AGENTS, README/ROADMAP, эксплуатацию, архитектурную модель и реестр данных.
