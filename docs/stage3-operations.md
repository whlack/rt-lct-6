# Каркас интеграций — API и эксплуатация

## Текущая готовность

Источники LMS и WEBSITE не реализованы. Каркас содержит очередь, историю и расписание, но не обращается к источникам и не изменяет вузы, контакты, каталоги, проекты или workflow. Ни URL, ни токен не могут включить эти интеграции: требуется реализация адаптеров по будущему контракту.

Первый запуск и обновление выполняются существующими `scripts/migrate.sh --local`, затем `scripts/start.sh --local`. На сервере используются готовые образы API и worker и существующий `scripts/deploy.sh --prod`; миграции не выполняются автоматически при start. Рабочие Compose-файлы, `.env` и секреты в Git не добавляются. Frontend nginx обслуживает только статические файлы; маршрутизация API принадлежит внешнему nginx.

## Через Swagger/API

Swagger UI: `/api/docs`. Требуется обычный Bearer-токен Keycloak. У прав `integrations.manage` и `integrations.sync` начальный уровень 20; администратор может изменить его. Seed не перезаписывает этот уровень.

`GET /api/integrations`:

```json
[
  {
    "source": "LMS",
    "availability": "NOT_IMPLEMENTED",
    "reason": "SOURCE_NOT_IMPLEMENTED",
    "intervalSeconds": 3600,
    "nextRunAt": null,
    "lastRun": null
  },
  {
    "source": "WEBSITE",
    "availability": "NOT_IMPLEMENTED",
    "reason": "SOURCE_NOT_IMPLEMENTED",
    "intervalSeconds": 3600,
    "nextRunAt": null,
    "lastRun": null
  }
]
```

`POST /api/integrations/LMS/sync` и аналогичный маршрут WEBSITE возвращают HTTP 409:

```json
{ "statusCode": 409, "message": "SOURCE_NOT_IMPLEMENTED", "error": "Conflict" }
```

Задание при этом не создаётся. `GET /api/integrations/LMS/runs?page=1&pageSize=25` возвращает `{ "rows": [], "total": 0, "page": 1, "pageSize": 25 }`. История доступна обладателям integrations.manage независимо от инициатора, поскольку отражает глобальные служебные операции, без предметных данных. `/runs/:id` возвращает только публичную проекцию задания.

Для будущего готового адаптера ручной запуск возвращает `202 {"runId":"<UUID>"}`; повтор при активном задании — 409 SYNC_ALREADY_ACTIVE. При отзыве права автора до выполнения ручное задание заканчивается ACCESS_UNAVAILABLE. Плановые задания не имеют автора и сейчас не создаются; границы доступа к прикладным данным для будущего адаптера нужно определить отдельно.

Ошибки: 400 — неверные UUID или пагинация; 401 — отсутствие/ошибка токена; 403 — недостаточное право; 404 — неизвестный источник/задание. Имена источников регистрозависимы: LMS и WEBSITE.

## Настройки и очередь

| Переменная                    | По умолчанию | Назначение                                       |
| ----------------------------- | ------------ | ------------------------------------------------ |
| LMS_SYNC_INTERVAL_SECONDS     | 3600         | Интервал LMS                                     |
| WEBSITE_SYNC_INTERVAL_SECONDS | 3600         | Интервал сайта                                   |
| SYNC_CONCURRENCY              | 1            | Число одновременно обрабатываемых заданий worker |
| SYNC_RUN_RETENTION_DAYS       | 90           | Хранение завершённой истории                     |

Значения должны быть положительными целыми. Проверка расписания каждые 30 секунд; доставка каждые 5 секунд. UTC-интервалы привязаны к Unix epoch; после простоя берётся текущий интервал, очередь пропущенных интервалов не создаётся. Для NOT_IMPLEMENTED расписание всегда пропускается.

PostgreSQL хранит статус QUEUED/RUNNING/SUCCEEDED/FAILED, аренду, попытки и сроки повтора; Redis `crm-sync` хранит только ID. Удаление Redis не означает потерю подтверждённой истории: диспетчер повторно доставляет незавершённые задания. Не удалять активные записи БД для исправления очереди.

Временные ошибки повторяются до трёх раз с задержками 10 и 20 секунд, либо большей задержкой Retry-After. INVALID_DATA, ACCESS_UNAVAILABLE и SOURCE_NOT_IMPLEMENTED окончательные. RETRY_EXHAUSTED означает сбой последней попытки до записи итога. Для восстановления сначала устранить инфраструктурную причину; новое ручное задание разрешено только после окончания предыдущего и только для реализованного источника.

Аренда — 30 секунд, продление — каждые 5 секунд. Потеря аренды отменяет адаптер через AbortSignal и запрещает запись результата старым исполнителем. Адаптер обязан соблюдать отмену и идемпотентность прикладных изменений; наличие очереди само по себе не обеспечивает однократность внешних эффектов.

Production-образы запускают непосредственно `node dist/main.js` и `node dist/worker.js`, чтобы SIGTERM достигал приложения. В серверном Compose сохранить CMD образа либо задать эти команды; не заменять их запуском через pnpm.

При остановке контейнера worker перестаёт принимать задания и ждёт текущую обработку в пределах существующего stop_grace_period. При принудительной остановке доставка восстанавливается после истечения аренды/блокировки Redis. Нереализованные источники не делают health/ready API недоступными.

## Наблюдение и резервирование

В существующих метриках crm_queue_jobs использовать queue=sync; crm_job_seconds, crm_job_wait_seconds, crm_job_errors_total и crm_job_retries_total используют kind=sync_lms/sync_website. crm_sync_runs_cleaned_total считает удалённые завершённые записи. Метрики API защищены существующим административным доступом, worker — внутренней сетью.

Логи содержат jobId, source и result. В API/журналы не попадают токены, профили, тела источников, execution ID и аренда. История включена в обычный PostgreSQL backup. В S3 интеграционные файлы не создаются. Использовать существующие backup.sh и restore-check.sh с единственным --local/--prod; восстановление проверять только на изолированном стенде.

Очистка в worker удаляет завершённые записи старше SYNC_RUN_RETENTION_DAYS; активные записи сохраняются. 90 дней — технический срок до согласования организационных требований. Обновлённая модель: `docs/architecture/crm-stage3.archimate`.

## Проверка каркаса

Обычные и Docker-интеграционные тесты используют тестовый адаптер; его нет в обычной сборке реестра источников. Существующий scripts/acceptance.sh --local/--prod запускает интеграционные тесты перед обычными API/worker на отдельной БД и Redis с ACCEPTANCE_ISOLATED=1. Без этого явного признака тест каркаса завершается ошибкой до подключения к БД. Они очищают свои задания и очередь crm-sync изолированного стенда.

Каркас считается проверенным после прохождения API, прав, восстановления доставки, повторов, аренды и остановки worker. Реальный обмен LMS/сайта и полная приёмка MVP остаются незавершёнными.
