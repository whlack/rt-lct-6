# CRM Ростелекома для работы с вузами

## Запуск CRM

Сервер CRM поддерживает вход через Keycloak, каталоги, вузы, проекты, этапы, документы, комментарии и историю. Клиентский интерфейс пока показывает публичное состояние API; его развитие выполняется отдельно. Учётные записи создаются в Keycloak; импорт realm не создаёт пользователей. Закрытие проекта после последнего этапа требует права `projects.close` с минимальным уровнем 20.

1. Скопируйте `.env.example` в `.env` и замените все пароли.
2. Скопируйте `docker-compose.yaml.example` в `docker-compose.yaml`.
3. Запустите `./scripts/migrate.sh --local`, затем `./scripts/start.sh --local`.
4. Откройте страницу состояния на `http://localhost:5173`, Swagger на `http://localhost:3000/api/docs`, Keycloak на `http://localhost:8080`.

`./scripts/status.sh --local` показывает состояние контейнеров, `./scripts/logs.sh --local` — последние журналы, `./scripts/stop.sh --local` останавливает стек без удаления томов. Повторный вызов `migrate.sh` безопасен: Prisma применяет только новые миграции, seed добавляет отсутствующие ключи прав и сохраняет изменённые администратором уровни. После изменения паролей БД в `.env` у уже созданного тома PostgreSQL необходимо согласовать их с существующими пользователями БД; init-скрипт выполняется только при первой инициализации тома.

Все команды находятся в `scripts/` и требуют ровно один флаг `--local` или `--prod`. Локальный `start.sh` использует Vite и Nest watch с подключённым исходным кодом; Vite проксирует `/api` в backend только в локальной разработке. Обычный старт не запускает миграции. Для production подготовьте на сервере игнорируемый `docker-compose.prod.yaml` с теми же сервисами, сетями и проверками готовности, но с полными именами и фиксированными тегами готовых образов `backend`, `frontend` и `migrate`; удалите `build` и bind mounts исходного кода, задайте production-команды для backend и веб-сервера frontend. Nginx внутри frontend-образа отдаёт только файлы Vite. Внешний nginx должен направлять `/api/*` в backend, а остальные пути — во frontend. Образ мигратора должен содержать Prisma CLI, миграции и seed. `./scripts/deploy.sh --prod` выполнит pull, миграцию и seed, затем запустит новую версию; при ошибке миграции запуск прервётся. Production-файл не хранится в Git.

Переменные `.env`: `POSTGRES_*` — начальный администратор PostgreSQL; `CRM_DB*` и `KEYCLOAK_DB*` — отдельные базы и учётные записи; `KEYCLOAK_ADMIN*` — административный доступ к Keycloak; `KEYCLOAK_*_ROLE` — имена ролей приложения (по умолчанию `kam`, `supervisor`, `admin`, совпадают с `infra/keycloak/realm.json`); `KEYCLOAK_PUBLIC_URL` — URL Keycloak в браузере и issuer токенов, `KEYCLOAK_INTERNAL_URL` — адрес сервиса в Docker, `KEYCLOAK_CLIENT_ID` — публичный OIDC-клиент; `FRONTEND_ORIGIN` — внешний origin CRM для redirect URI и Web Origin клиента Keycloak; `S3_*` — адрес, регион, бакет и ключи S3-совместимого хранилища; `FRONTEND_PORT`, `API_PORT`, `KEYCLOAK_PORT`, `MINIO_PORT` — опубликованные локальные порты. В production задайте `FRONTEND_ORIGIN` и `KEYCLOAK_PUBLIC_URL` через `.env`, направьте внешний nginx на статический frontend и `/api` на backend, настройте внешний S3 и уберите локальные `minio`/`minio-setup` и зависимость backend от `minio-setup` из серверного Compose. Локальный MinIO запускается из фиксированного [community build](https://github.com/golithus/minio-builds), поскольку официальный образ больше не публикуется. Realm импортируется без пользовательских учётных записей. Redis развёрнут, но пока не используется приложением. Таблицы CRM изменяются только миграциями из `backend/prisma/`.

Краткая фиксация обсуждённых решений и черновой план MVP. Требования исходного ТЗ и дополнительные продуктовые решения отмечены отдельно.

## Продукт и модель данных

- CRM сотрудников ИТ Школы Ростелекома для работы с вузами и проектами сотрудничества.
- Вуз — центральный объект навигации. В карточке вуза видны все его проекты и основной контакт.
- **Проект привязан к одному вузу и формируется из двух основных полей: ИТ-направление/специальность и программа или продукт.** У проекта свои ответственные, workflow, этапы, файлы, комментарии и история действий. В исходном ТЗ ИТ-программа — учебные материалы и практика по направлению, ИТ-продукт — ПО для обучения; отдельное обязательное поле программы наряду с продуктом для проекта не вводим.
- Каталоги — централизованные списки вузов, направлений, программ/ИТ-продуктов и ответственных. Значения выбираются из справочников, а не вводятся заново в каждом проекте. Обновление каталогов через XLS/XLSX требуется ТЗ; подробный маппинг приложенных шаблонов отложен.
- Для пользователя в текущей CRM храним только минимальные необходимые поля; точный обязательный профиль ещё определить. Расширенные поля анкеты ниже сохранены как важная схема источника, но пока не входят в CRM. По требованию заказчика их можно реализовать отдельными полями; на первом этапе дополнительную информацию можно вносить одним текстовым полем/комментарием.

### Поля из ТЗ и приложенных шаблонов

**Каталог/загрузка данных по ТЗ** предусматривает каталоги вузов, ИТ-направлений, ИТ-продуктов и ответственных. В перечне полей ТЗ также указаны:

- название вуза;
- вендор;
- ПО;
- номер договора;
- подписание лицензии;
- срок действия лицензии (год);
- статус передачи;
- ФИО менеджера;
- ответственные от вуза;
- комментарий.

Вендор, номер договора, статус/подписание и срок действия лицензии, а также статус передачи относятся к проекту. Точный формат полей и маппинг импорта определим при реализации соответствующих экранов и загрузки данных. Поле «ПО» сопоставляется с выбранным продуктом, если для проекта выбран именно продукт.

**`Вендоры.xlsx`**, лист `Лист1`, содержит колонки: `Компания`, `Продукт`, `ФИО`, `Телефон`, `Почта`, `Способ связи`. Это шаблон списка компаний-вендоров, их продуктов и контактов.

**`Загрузка пользователей.xlsx`**, лист `Лист1`, содержит следующие заголовки:

- Фамилия; Имя; Отчество (при наличии); Номер телефона; Email;
- СНИЛС; Серия паспорта; Номер паспорта; Кем выдан паспорт; Дата выдачи паспорта; Код подразделения;
- Пол; Дата рождения;
- Регион регистрации; Населённый пункт регистрации; Улица регистрации; Дом регистрации; Квартира регистрации; Индекс регистрации;
- Имя в дательном падеже; Фамилия в дательном падеже; Отчество в дательном падеже;
- Образование; Профессия по диплому; Учебное заведение по диплому; Фамилия, указанная в дипломе; Номер диплома; Серия диплома; Регистрационный номер диплома; Дата выдачи диплома.

В `Лист2` даны значения для пола (`М`, `Ж`) и образования: без образования; основное общее (9 классов); среднее общее (11 классов); среднее профессиональное; высшее — бакалавриат; высшее — специалитет/магистратура; высшее — подготовка кадров высшей квалификации.

**`Данные оплат.json`** содержит массив объектов с полями: `Номер заявки`, `Курс`, `Фамилия`, `Имя`, `Отчество`, `Телефон`, `Email`, `Номер потока`. В приложенном примере первый элемент массива `null`. Несмотря на название файла, поля суммы, статуса и даты оплаты в структуре примера отсутствуют. Это образец данных, а не утверждённый контракт интеграции.

В сводку включены только заголовки и структура полей, без персональных значений из строк примеров. СНИЛС, паспортные данные, адрес и сведения о дипломе не включать в начальный объём CRM без отдельного требования заказчика.

## Workflow, документы и комментарии

- Проект создаётся со стандартным workflow на основе этапов из ТЗ.
- Первый этап называется **«Формирование проекта»**. Он системный: его нельзя удалить, переименовать или изменить.
- Остальные этапы можно настраивать, пока проект находится на начальном этапе «Формирование проекта». После выхода проекта из него состав этапов фиксируется.
- Настройка workflow требует отдельного права с минимальным уровнем **руководитель КАМ (20)**; администратор также имеет доступ.
- Рабочий workflow показывается горизонтальной канвой карточек этапов с фокусом на текущем этапе.
- У документа один флаг: `is_required`. Если обязательный документ не приложен, переход дальше заблокирован. Отдельный `is_blocker` не используем.
- К этапам прикладываются файлы форматов PNG, JPEG, PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS, XLSX.
- Комментарии поддерживают ответы, редактирование и удаление.
- История проекта фиксирует переходы между этапами, подписание, прикрепление и завершение файлов, закрытие проекта, назначение руководителя/ответственного и другие значимые изменения. События связываются с пользователем, временем и затронутым объектом.

Базовый процесс ТЗ охватывает поиск контакта, коммуникации и встречи; обмен, корректировку и подписание документов; передачу учебных материалов и лицензии; внедрение продукта; обучение преподавателей и актуализацию программы; занятия, обновление документации, повышение квалификации и контроль этапов.

## Главная, отчёты, интеграции

- Главная показывает количество вузов-партнёров, активных проектов и проектов, требующих действий. Отдельного счётчика программ нет. Разделения B2B/B2C нет.
- Проект требует действия, если он открыт и текущий этап имеет expectedActor = KAM. Личное назначение текущего пользователя не является дополнительным условием; применяется обычная область видимости.
- Отчёты доступны на отдельной странице. Для отчёта по периоду пользователь задаёт даты; общий отчёт по проекту включает даты событий автоматически.
- Контракты отчётов, импорта и статистики зафиксированы в [руководстве серверного API](./docs/stage2-api.md): фильтры, состав сводки и общего отчёта, XLS/XLSX/PDF и PNG/PDF.
- Интеграции с LMS ИТ Школы и сайтом на Laravel входят в MVP на этапе 3 и в критерии его приёмки. Данные поступают по API в JSON и могут включать согласованные поля источника. Контракты и маппинг согласовать с командами до реализации. Интеграцию с Контуром убрали.

## Роли и доступ

- Авторизация — Keycloak. Имена ролей руководителя и администратора задаются настройками приложения, например `KEYCLOAK_SUPERVISOR_ROLE`, `KEYCLOAK_ADMIN_ROLE`.
- Уровни: **КАМ (менеджер по вузам) — 10**, **руководитель КАМ — 20**, **администратор — 30**.
- Для каждого экрана и значимой операции задаётся право и минимальный уровень; права хранятся в БД и проверяются на сервере.
- Перед реализацией каждого нового экрана/права Codex запрашивает у пользователя ключ права и минимальный уровень.
- Настройка workflow доступна от руководителя КАМ и выше, при наличии соответствующего права.
- Область видимости данных отделена от уровня роли. Руководитель может назначать, менять и удалять ответственных за вузы; администратор управляет правами и ограничениями видимости.

## Технологии и ограничения ТЗ

- Frontend: React. Backend: Node.js + NestJS.
- PostgreSQL для хранения данных; Redis — для очередей BullMQ. Кэширование добавляется только при подтверждённой измерениями необходимости.
- Отклик интерфейсных операций — до 1 секунды; нагрузка — 50 параллельных пользователей и 10 параллельных отчётов. Проверяем нагрузочным тестированием при приёмке.
- Поддержка Linux и Docker, API со Swagger UI, веб-интерфейс для компьютера и мобильных устройств, работа без полной перезагрузки страниц.
- ТЗ также требует пользовательскую и административную документацию со скриншотами, документацию по сборке/установке и описание архитектуры в Archi; требования 152-ФЗ и приказа ФСТЭК №117.
