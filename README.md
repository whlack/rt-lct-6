# CRM Ростелекома для работы с вузами

## Запуск CRM

CRM поддерживает корпоративный вход через Keycloak, вузы и контакты, каталоги, проекты, этапы, документы, комментарии, историю, отчёты, статистику и импорт. Клиент использует реальные API и права пользователя. Учётные записи создаются в Keycloak; импорт realm не создаёт пользователей. Закрытие проекта после последнего этапа требует права `projects.close` с минимальным уровнем 20.

1. Скопируйте `.env.example` в `.env` и замените все пароли.
2. Скопируйте `docker-compose.yaml.example` в `docker-compose.yaml`.
3. Запустите `./scripts/migrate.sh --local`, затем `./scripts/start.sh --local`.
4. Откройте CRM по адресу `FRONTEND_ORIGIN` (в примере `http://localhost:5173`), публичную диагностику по адресу `FRONTEND_ORIGIN/status`, Swagger (вне production) на `http://localhost:3000/api/docs`, Keycloak на `http://localhost:8080`.

### Локальные учётные записи

`./scripts/start.sh --local` создаёт тестовые учётные записи в локальном realm `crm`:

| Логин        | Пароль       | Группа       | Роль CRM      |
| ------------ | ------------ | ------------ | ------------- |
| `kam`        | `kam`        | `kam`        | КАМ           |
| `supervisor` | `supervisor` | `supervisor` | Руководитель  |
| `admin`      | `admin`      | `admin`      | Администратор |

Группа и назначенная ей роль имеют одноимённые ключи `kam`, `supervisor`, `admin`. Роль также назначается пользователю напрямую: каталог сотрудников CRM запрашивает у Keycloak прямых участников роли. Тестовый `admin` — пользователь CRM, а не администратор Keycloak realm `master`. Создание можно повторить командой `./scripts/seed-local-users.sh --local`; повторный запуск сохраняет изменённые вручную пароли. Эти простые пароли предназначены только для локального стенда; production-запуск пользователей не создаёт.

Клиент получает только публичные параметры OIDC из `GET /api/config` во время запуска. Секреты и адреса окружения не встраиваются в клиентскую сборку; `KEYCLOAK_PUBLIC_URL`, `KEYCLOAK_REALM`, `KEYCLOAK_CLIENT_ID` и `FRONTEND_ORIGIN` задаются в едином `.env`. Вход использует Authorization Code + PKCE; токены остаются в памяти. Смена прав и области видимости сбрасывает клиентский кэш. Выбранная светлая/тёмная тема — единственная сохраняемая настройка браузера.

Рабочие сценарии и административные действия описаны в [руководстве клиента](./docs/frontend/guide.md); устройство клиента, проверки и отличия от прототипа — в [техническом описании](./docs/frontend/architecture.md) и [анализе дизайна](./docs/frontend/design-review.md). Дизайнерский прототип перенесён в рабочий клиент; отдельный каталог его исходников удалён.

Если Keycloak возвращает `Invalid parameter: redirect_uri`, сравните origin открытой страницы с `FRONTEND_ORIGIN`. Например, `http://localhost:5173` и `http://127.0.0.1:5173` — разные адреса; в примере разрешён первый. Откройте настроенный адрес либо измените `FRONTEND_ORIGIN` в `.env` и повторно запустите настройку клиента: `docker compose --env-file .env -f docker-compose.yaml run --rm keycloak-config` (для production используйте свой серверный Compose-файл). Затем откройте CRM заново. Перезапуск frontend или изменение `VITE_*` не обновляет разрешённые redirect URI в Keycloak. Данные и тома удалять не требуется.

`./scripts/status.sh --local` показывает состояние контейнеров, `./scripts/logs.sh --local` — последние журналы, `./scripts/stop.sh --local` останавливает стек без удаления томов. Повторный вызов `migrate.sh` безопасен: Prisma применяет только новые миграции, seed добавляет отсутствующие ключи прав и сохраняет изменённые администратором уровни. Локальный `start.sh` дополнительно создаёт отсутствующие тестовые группы и учётные записи в Keycloak. После изменения паролей БД в `.env` у уже созданного тома PostgreSQL необходимо согласовать их с существующими пользователями БД; init-скрипт выполняется только при первой инициализации тома.

Все команды находятся в `scripts/` и требуют ровно один флаг `--local` или `--prod`. Локальный `start.sh` использует Vite и Nest watch с подключённым исходным кодом; Vite проксирует `/api` в backend только в локальной разработке. Обычный старт не запускает миграции. Для production подготовьте на сервере игнорируемый `docker-compose.prod.yaml` с теми же сервисами, сетями и проверками готовности, но с полными именами и фиксированными тегами готовых образов `backend`, `frontend` и `migrate`; удалите `build` и bind mounts исходного кода, задайте production-команды для backend и веб-сервера frontend. Для frontend используйте target `production`, порт контейнера 80 и стандартный entrypoint образа. Nginx внутри frontend отдаёт файлы Vite и проксирует `/api/*` в `API_UPSTREAM`, подставляемый при запуске. Внешний nginx завершает TLS и направляет запросы CRM во frontend; отдельное правило `/api` с прямым upstream backend также допустимо. Используйте target `production` для API, `worker-production` для worker и `tooling` для migrate, keycloak-config и minio-setup. Runtime API/worker работают от пользователя node с production-зависимостями; команды миграции и seed запускаются в отдельном образе tooling. Prisma/TypeScript остаются транзитивными optional peer-зависимостями @prisma/client, но не доступны как прямые команды приложения. `./scripts/deploy.sh --prod` выполнит pull, миграцию и seed, затем запустит новую версию; при ошибке миграции запуск прервётся. Production-файл не хранится в Git.

Переменные `.env`: `POSTGRES_*` — начальный администратор PostgreSQL; `CRM_DB*` и `KEYCLOAK_DB*` — отдельные базы и учётные записи; `KEYCLOAK_ADMIN*` — административный доступ только для начальной настройки Keycloak; `KEYCLOAK_SERVICE_CLIENT_ID` и `KEYCLOAK_SERVICE_CLIENT_SECRET` — отдельный конфиденциальный клиент для чтения сотрудников; `KEYCLOAK_*_ROLE` — имена ролей приложения (по умолчанию `kam`, `supervisor`, `admin`, совпадают с `infra/keycloak/realm.json`); `KEYCLOAK_PUBLIC_URL` — URL Keycloak в браузере и issuer токенов, `KEYCLOAK_INTERNAL_URL` — адрес сервиса в Docker, `KEYCLOAK_CLIENT_ID` — публичный OIDC-клиент; `FRONTEND_ORIGIN` — внешний origin CRM для redirect URI и Web Origin клиента Keycloak (точные схема, домен/IP и порт, без пути); `API_UPSTREAM` — адрес backend, доступный из frontend-контейнера, без `/api` и завершающего `/` (по умолчанию `http://backend:3000`); `S3_*` — адрес, регион, бакет и ключи S3-совместимого хранилища; `FRONTEND_PORT`, `API_PORT`, `KEYCLOAK_PORT`, `MINIO_PORT` — опубликованные локальные порты. В production задайте `FRONTEND_ORIGIN` и `KEYCLOAK_PUBLIC_URL` через `.env`, передайте `API_UPSTREAM` в environment frontend и направьте внешний nginx во frontend на порт 80, настройте внешний S3 и уберите локальные `minio`/`minio-setup` и зависимость backend от `minio-setup` из серверного Compose. Локальный MinIO запускается из фиксированного [community build](https://github.com/golithus/minio-builds), поскольку официальный образ больше не публикуется. Realm импортируется без пользовательских учётных записей; только локальный `start.sh` создаёт три тестовые записи. Redis доставляет задания экспорта, импорта и синхронизации через BullMQ; подтверждённые состояния хранятся в PostgreSQL. Таблицы CRM изменяются только миграциями из `backend/prisma/`.

`KEYCLOAK_REALM` задаёт имя realm для входа, проверки токенов, каталога сотрудников и настройки клиентов; при отсутствии переменной используется `crm`. Встроенный `infra/keycloak/realm.json` импортирует только `crm`, поэтому другой realm во внешнем Keycloak должен существовать заранее. При смене realm передайте `KEYCLOAK_REALM` в backend, worker и `keycloak-config` через серверный Compose; браузер получит имя realm из `/api/config`. Публичный URL Keycloak должен совпадать с issuer токенов выбранного realm.

Краткая фиксация обсуждённых решений и черновой план MVP. Требования исходного ТЗ и дополнительные продуктовые решения отмечены отдельно.

## Продукт и модель данных

- CRM сотрудников ИТ Школы Ростелекома для работы с вузами и проектами сотрудничества.
- Вуз — центральный объект навигации. В карточке вуза видны все его проекты и основной контакт.
- **Проект привязан к одному вузу и формируется из двух основных полей: ИТ-направление/специальность и программа или продукт.** У проекта свои ответственные, workflow, этапы, файлы, комментарии и история действий. В исходном ТЗ ИТ-программа — учебные материалы и практика по направлению, ИТ-продукт — ПО для обучения; отдельное обязательное поле программы наряду с продуктом для проекта не вводим.
- Каталоги — централизованные списки вузов, направлений, программ/ИТ-продуктов и ответственных. Значения выбираются из справочников, а не вводятся заново в каждом проекте. Обновление каталогов через XLS/XLSX требуется ТЗ; подробный маппинг приложенных шаблонов отложен.
- Для пользователя в текущей CRM храним только минимальные необходимые поля. Расширенные поля анкеты ниже сохранены как важная схема источника, но пока не входят в CRM. По требованию заказчика их можно реализовать отдельными полями; на первом этапе дополнительную информацию можно вносить одним текстовым полем/комментарием.

## Решения этапа 0

### Обязательные поля и участники

| Объект            | Обязательные поля при создании                                              |
| ----------------- | --------------------------------------------------------------------------- |
| Вуз               | Название                                                                    |
| Контакт вуза      | Вуз, ФИО, хотя бы один способ связи: email или телефон                      |
| Ответственный КАМ | Существующая учётная запись Keycloak с идентификатором, email и ФИО         |
| Проект            | Вуз, ИТ-направление/специальность, программа или продукт, ответственный КАМ |

Ответственный КАМ проекта выбирается из существующих пользователей Keycloak. Контакт вуза — отдельная запись с контактными данными без учётной записи Keycloak. Вендор, номер договора, сведения о подписании и сроке действия лицензии, статус передачи относятся к проекту, но при его создании необязательны. Форматы и возможные значения этих проектных полей уточняются при реализации соответствующего экрана.

### Стандартный workflow

1. Формирование проекта.
2. Поиск контакта и согласование.
3. Документы и подписание.
4. Передача материалов и лицензий.
5. Внедрение программы или продукта.
6. Обучение преподавателей.
7. Проведение занятий.
8. Сопровождение и контроль.

Первый этап системный и неизменяемый. Пока проект находится на нём, пользователь с правом `projects.workflow.configure` и уровнем не ниже 20 может добавлять, переименовывать, переставлять и удалять остальные этапы. После перехода с первого этапа состав и порядок этапов фиксируются.

### Права первых экранов и операций

Администратор задаёт видимость КАМ: по назначениям, все данные или список разрешённых вузов/проектов. Руководители и администраторы видят всё. Подробный контракт — в [руководстве API](./docs/stage2-api.md).

Минимальный уровень права хранится в БД. Каждый ключ проверяется на сервере; область видимости данных проверяется отдельно. Для реализации первых экранов и операций согласованы следующие ключи:

| Ключ                            | Операция                                            | Уровень |
| ------------------------------- | --------------------------------------------------- | ------: |
| `universities.read`             | Просмотр списка и карточки вузов                    |      10 |
| `universities.create`           | Создание вуза                                       |      10 |
| `universities.update`           | Изменение вуза                                      |      10 |
| `university_contacts.read`      | Просмотр контактов вуза                             |      10 |

| `university_contacts.update`    | Изменение контакта вуза                             |      10 |
| `catalogs.read`                 | Просмотр направлений, программ и продуктов          |      10 |
| `catalogs.manage`               | Ведение направлений, программ и продуктов           |      20 |
| `catalogs.import`               | Импорт и актуализация каталогов                     |      20 |
| `projects.read`                 | Просмотр списка и карточки проектов                 |      10 |

### Импорт каталогов

Базовый шаблон — [одна книга XLSX](./docs/templates/catalog-import.xlsx) с листами `Вузы`, `Направления`, `Программы и продукты`, `Сотрудники`. Лист сотрудников сопоставляется с существующими пользователями Keycloak по email; импорт не создаёт учётные записи.

### Внешние запросы для интеграций

[Готовые тексты двух запросов](./docs/integration-contract-requests.md) адресованы командам LMS и сайта на Laravel. Владелец проекта отправляет их по рабочим каналам и фиксирует адресата, дату и ссылку на переписку в этом документе. Получение контрактов и тестовых JSON необходимо до реализации интеграций этапа 3.

### Поля из ТЗ и приложенных шаблонов

**Каталог/загрузка данных по ТЗ** предусматривает каталоги вузов, ИТ-направлений, ИТ-продуктов и ответственных. В перечне полей ТЗ также указаны:

- название вуза;
- вендор;
- ПО;
- номер договора;
- подписание лицензии;
- срок действия лицензии (год);
- статус передачи;
- ФИО менеджера;
- ответственные от вуза;
- комментарий.

Вендор, номер договора, статус/подписание и срок действия лицензии, а также статус передачи относятся к проекту. Точный формат полей и маппинг импорта определим при реализации соответствующих экранов и загрузки данных. Поле «ПО» сопоставляется с выбранным продуктом, если для проекта выбран именно продукт.

**`Вендоры.xlsx`**, лист `Лист1`, содержит колонки: `Компания`, `Продукт`, `ФИО`, `Телефон`, `Почта`, `Способ связи`. Это шаблон списка компаний-вендоров, их продуктов и контактов.

**`Загрузка пользователей.xlsx`**, лист `Лист1`, содержит следующие заголовки:

- СНИЛС; Серия паспорта; Номер паспорта; Кем выдан паспорт; Дата выдачи паспорта; Код подразделения;
- Пол; Дата рождения;
- Регион регистрации; Населённый пункт регистрации; Улица регистрации; Дом регистрации; Квартира регистрации; Индекс регистрации;
- Имя в дательном падеже; Фамилия в дательном падеже; Отчество в дательном падеже;
- Образование; Профессия по диплому; Учебное заведение по диплому; Фамилия, указанная в дипломе; Номер диплома; Серия диплома; Регистрационный номер диплома; Дата выдачи диплома.

В `Лист2` даны значения для пола (`М`, `Ж`) и образования: без образования; основное общее (9 классов); среднее общее (11 классов); среднее профессиональное; высшее — бакалавриат; высшее — специалитет/магистратура; высшее — подготовка кадров высшей квалификации.

**`Данные оплат.json`** содержит массив объектов с полями: `Номер заявки`, `Курс`, `Фамилия`, `Имя`, `Отчество`, `Телефон`, `Email`, `Номер потока`. В приложенном примере первый элемент массива `null`. Несмотря на название файла, поля суммы, статуса и даты оплаты в структуре примера отсутствуют. Это образец данных, а не утверждённый контракт интеграции.

В сводку включены только заголовки и структура полей, без персональных значений из строк примеров. СНИЛС, паспортные данные, адрес и сведения о дипломе не включать в начальный объём CRM без отдельного требования заказчика.

## Workflow, документы и комментарии

- Проект создаётся со стандартным workflow на основе этапов из ТЗ.
- Первый этап называется **«Формирование проекта»**. Он системный: его нельзя удалить, переименовать или изменить.
- Остальные этапы можно настраивать, пока проект находится на начальном этапе «Формирование проекта». После выхода проекта из него состав этапов фиксируется.
- Настройка workflow требует отдельного права с минимальным уровнем **руководитель КАМ (20)**; администратор также имеет доступ.
- Рабочий workflow показывается горизонтальной канвой карточек этапов с фокусом на текущем этапе.
- У документа один флаг: `is_required`. Если обязательный документ не приложен, переход дальше заблокирован. Отдельный `is_blocker` не используем.
- К этапам прикладываются файлы форматов PNG, JPEG, PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS, XLSX.
- Комментарии поддерживают ответы, редактирование и удаление.
- История проекта фиксирует переходы между этапами, подписание, прикрепление и завершение файлов, закрытие проекта, назначение руководителя/ответственного и другие значимые изменения. События связываются с пользователем, временем и затронутым объектом.

Базовый процесс ТЗ охватывает поиск контакта, коммуникации и встречи; обмен, корректировку и подписание документов; передачу учебных материалов и лицензии; внедрение продукта; обучение преподавателей и актуализацию программы; занятия, обновление документации, повышение квалификации и контроль этапов.

## Главная, отчёты, интеграции

- Главная показывает количество вузов-партнёров, активных проектов и проектов, требующих действий. Отдельного счётчика программ нет. Разделения B2B/B2C нет.
- Проект требует действия, если он открыт и текущий этап имеет expectedActor = KAM. Личное назначение текущего пользователя не является дополнительным условием; применяется обычная область видимости.
- Отчёты доступны на отдельной странице. Для отчёта по периоду пользователь задаёт даты; общий отчёт по проекту включает даты событий автоматически.
- Контракты отчётов, импорта и статистики зафиксированы в [руководстве серверного API](./docs/stage2-api.md): фильтры, состав сводки и общего отчёта, XLS/XLSX/PDF/JSON с выбором колонок и PNG/PDF.
- Интеграции с LMS ИТ Школы и сайтом на Laravel входят в MVP на этапе 3 и в критерии его приёмки. Данные поступают по API в JSON и могут включать согласованные поля источника. Контракты и маппинг согласовать с командами до реализации. Интеграцию с Контуром убрали.

## Роли и доступ

- Авторизация — Keycloak. Имена ролей руководителя и администратора задаются настройками приложения, например `KEYCLOAK_SUPERVISOR_ROLE`, `KEYCLOAK_ADMIN_ROLE`.
- Уровни: **КАМ (менеджер по вузам) — 10**, **руководитель КАМ — 20**, **администратор — 30**.
- Для каждого экрана и значимой операции задаётся право и минимальный уровень; права хранятся в БД и проверяются на сервере.
- Ключи и уровни первых экранов согласованы в разделе «Решения этапа 0». Перед реализацией каждого нового экрана или права за пределами этого перечня Codex запрашивает у пользователя ключ и минимальный уровень.
- Настройка workflow доступна от руководителя КАМ и выше, при наличии соответствующего права.
- Область видимости данных отделена от уровня роли. Руководитель может назначать, менять и удалять ответственных за вузы; администратор управляет правами и ограничениями видимости.

## Технологии и ограничения ТЗ

- Frontend: React. Backend: Node.js + NestJS.
- PostgreSQL для хранения данных; Redis — для очередей BullMQ. Кэширование добавляется только при подтверждённой измерениями необходимости.
- Приёмочный критерий отклика — p95 каждой интерактивной операции ≤1 секунды; нагрузка — 50 параллельных пользователей и 10 параллельных отчётов. Проверяем нагрузочным тестированием; максимумы сохраняем отдельно, ожидание фоновых заданий не включаем в интерактивные измерения.
- Поддержка Linux и Docker, API со Swagger UI, веб-интерфейс для компьютера и мобильных устройств, работа без полной перезагрузки страниц.
- ТЗ также требует пользовательскую и административную документацию со скриншотами, документацию по сборке/установке и описание архитектуры в Archi; требования 152-ФЗ и приказа ФСТЭК №117.

## Обновление после ревью бэкенда

В существующий `.env` добавьте `KEYCLOAK_SERVICE_CLIENT_ID=crm-directory` и уникальный `KEYCLOAK_SERVICE_CLIENT_SECRET`. В рабочем Compose перенесите настройки из примера: административные credentials остаются только у Keycloak и keycloak-config, API/worker получают service credentials. Для production используйте отдельный образ tooling для миграции и настройки клиентов. Выполните migrate и перезапустите стек; исходные данные не требуется пересоздавать.

Правила видимости КАМ и обновлённые контракты списка проектов, JSON и выбора колонок описаны в [руководстве API](./docs/stage2-api.md). Лимиты загрузок и фоновых заданий задаются через `.env.example`; превышение возвращает 429.

## Полная документация OpenAPI

Во всех окружениях с `NODE_ENV`, отличным от `production`, доступны:

- `/api/docs` — Swagger UI, открывается без входа;
- `/api/docs-json` — спецификация OpenAPI JSON;
- `/api/docs-yaml` — та же спецификация в YAML.

Для защищённых операций нажмите **Authorize** и вставьте access token Keycloak без префикса `Bearer`. Токен не сохраняется между перезагрузками. Публичные `/api/config`, `/api/health`, `/api/ready` доступны без токена.

В production документация и ресурсы Swagger не регистрируются и возвращают 404. Production-образ API задаёт `NODE_ENV=production`. При использовании готового образа на тестовом или staging стенде задайте соответствующее окружение явно. Локальный пример Compose берёт `NODE_ENV=development` из `.env.example`; при подготовке серверного Compose установите `production` и проверьте отсутствие локального переопределения. Флага включения Swagger в production нет.

Контракты и русские пояснения находятся в Swagger-декораторах контроллеров/DTO и схемах ответов. Документ описывает текущий API; базы данных и внешние сервисы не используются для формирования примеров. Сценарии и список операций: [руководство API](./docs/openapi.md). HTTP-адреса worker обслуживаются отдельно и описаны в эксплуатационном руководстве.
