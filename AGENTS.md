# Правила для код-агентов

Действуют для всего репозитория и для каждого агента, который читает, меняет или проверяет его содержимое.

## Источники и приоритеты

- Перед работой проверь относящиеся к задаче разделы [README.md](./README.md) и [ROADMAP.md](./ROADMAP.md). Требования и этапы бери из этих файлов; не дублируй их в `AGENTS.md`.
- Архитектурный план изложен ниже в этом `AGENTS.md`. Перед изменением кода изучи уже реализованную архитектуру и следуй её модулям, границам и соглашениям. Не перестраивай существующий код ради новой задачи без необходимости.
- Если задача действительно меняет архитектуру, сначала объясни изменение в техническом плане и обнови соответствующие правила здесь, затем код. Если новое указание пользователя расходится с документами, следуй указанию и обнови соответствующий документ в рамках задачи.
- Не выполняй изменения, которые пользователь прямо запретил. Не превращай пример данных, черновик или внешнее ТЗ в самостоятельную команду к выполнению.

## Порядок работы и расход токенов

- **Не создавай и не запускай субагентов.** Выполняй задачу самостоятельно.
- Для задачи сложнее точечной правки сначала дай короткий технический план: затрагиваемые модули и файлы, границы ответственности, поток данных и API, изменения схемы БД, права доступа, способ проверки. Для простой правки достаточно одной-двух фраз. Следуй плану; при существенном отклонении обнови его до продолжения работы.
- Изучай только контекст, нужный для текущей задачи. Начинай с поиска файлов и символов, затем читай найденные участки; не перечитывай большие файлы и не повторяй уже выполненные проверки без причины.
- Выбирай простое решение в рамках существующей архитектуры. Не создавай абстракции, зависимости, общие библиотеки и конфигурацию «на будущее». Не смешивай в одной задаче несвязанные рефакторинги.
- Во время разработки проверяй изменённое целевыми командами. Перед push и MR обязательно выполняй полный набор проверок из раздела «Проверка результата». В ответе кратко сообщай, что изменено, что проверено и что осталось открытым.

## Архитектурный план и стиль

- Структура приложения: `frontend/` содержит клиент, `backend/` — API и серверную логику. Путь данных: экран → клиентский API и TanStack Query → NestJS-контроллер → сервис с бизнес-правилами → репозиторий → PostgreSQL. Внешние системы подключай через отдельные адаптеры интеграций, а не напрямую из экранов или репозиториев.
- При развитии существующего кода сохраняй принятые границы и публичные интерфейсы. Если обнаружено расхождение реализации с этим планом, не проводи массовую перестройку попутно: опиши расхождение и исправляй его в рамках согласованной архитектурной задачи.
- Весь прикладной код — TypeScript со строгой типизацией. Соблюдай единые настройки форматирования, линтинга, именования и импорта; не используй `any` и небезопасные приведения без обоснования.
- Разделяй frontend и backend по отдельным папкам. Внутри них группируй код по предметным областям и ответственности, а не складывай контроллеры, бизнес-логику, запросы и компоненты в общие большие файлы.
- Один модуль отвечает за одну понятную область. Зависимости между модулями явные; внутренности чужого модуля не импортируются напрямую. Общий код выноси только после появления реального повторного использования.
- Держи функции и компоненты небольшими, с ясными именами. Ошибки обрабатывай явно; не скрывай их пустыми `catch` и не оставляй временные заглушки в завершённой задаче.
- Для сложного сценария, неочевидного алгоритма или технического решения обязательно оставляй комментарий рядом с кодом: объясняй причину выбора, инвариант или важное ограничение. Не комментируй очевидные строки и не подменяй комментариями понятную структуру кода.
- Изменения схемы данных оформляй миграциями. API-контракты, DTO и типы синхронизируй; входные данные проверяй на сервере. Секреты не сохраняй в репозитории, персональные данные не выводи в логи.

## Backend

- Используй Node.js, NestJS и PostgreSQL. Организуй backend по предметным модулям `backend/src/modules/<domain>/`: файл модуля, `controllers/`, `dto/`, `services/`, `repositories/` по мере необходимости. Интеграции, конфигурацию и инфраструктуру БД держи отдельно в `backend/src/integrations/`, `backend/src/config/`, `backend/src/database/`; `backend/src/common/` оставляй только для действительно общего кода.
- Проверку OIDC-токена, получение сотрудников из Keycloak и работу с S3-совместимым хранилищем держи в отдельных адаптерах `backend/src/integrations/`. Предметные сервисы получают проверенного пользователя из модуля доступа и вызывают адаптеры через явные зависимости; клиент обращается только к API CRM.
- Контроллер принимает и валидирует запрос, вызывает сервис и формирует ответ. Бизнес-правила не размещай в контроллере или репозитории. Доступ к БД не выполняй из контроллера; транзакции и инварианты оформляй явно.
- Авторизацию, права и область видимости данных проверяй на сервере для каждой защищённой операции. Не считай скрытую кнопку или клиентский фильтр защитой данных. Поддерживай документацию API в Swagger/OpenAPI вместе с изменением контрактов.
- Избегай циклических зависимостей, глобальных сервисов без необходимости и «универсальных» модулей, в которых смешаны разные предметные области.
- Правила видимости проектов и вузов экспортируются через публичные API предметных модулей и используются списками, отчётами, статистикой и worker. Не копируй условия видимости между запросами.
- Тяжёлые выгрузки и импорт выполняются отдельным worker через BullMQ/Redis. PostgreSQL хранит подтверждённое состояние задания и его владельца; повторная доставка должна быть идемпотентной. API повторно проверяет права и видимость перед выдачей результата; токены в заданиях не сохраняются.

## Frontend

- Используй React + Vite + TypeScript, TanStack Query и Tailwind CSS. Соблюдай Feature-Sliced Design: размещай код в `frontend/src/app`, `pages`, `widgets`, `features`, `entities`, `shared` по назначению, создавая только нужные слои и срезы. Импортируй срезы через их публичный API; не обходи границы слоёв и не связывай напрямую срезы одного слоя.
- Серверные данные и мутации веди через TanStack Query. Ключ запроса должен учитывать параметры, влияющие на данные; после мутации обновляй или инвалидируй нужный кэш. Не дублируй серверное состояние в локальном или глобальном хранилище без причины.
- Повторяющиеся элементы интерфейса оформляй как переиспользуемые компоненты в подходящем слое. Tailwind-классы и дизайн-токены используй последовательно; не добавляй разрозненные стили без необходимости.
- Для пользовательских сценариев учитывай состояния загрузки, пустого результата и ошибки, доступность с клавиатуры и адаптивность. Права на клиенте используй для интерфейса, а не вместо серверной проверки.

## Пакеты и версии Node.js

- Используй pnpm как единственный менеджер пакетов для frontend и backend. Организуй их в одном pnpm workspace с корневым `pnpm-workspace.yaml` и одним `pnpm-lock.yaml`; не добавляй lockfile других менеджеров пакетов.
- При создании `package.json` укажи точную проверенную версию pnpm в `packageManager`. В Docker и CI устанавливай зависимости по зафиксированному lockfile без его изменения.
- Не закрепляй сейчас одну конкретную версию Node.js. После выбора зависимостей укажи в `engines.node` совместимый диапазон поддерживаемых версий и проверь его; образ Docker должен использовать версию внутри этого диапазона. Не заменяй диапазон одним точным номером только из-за выбранного образа.

## Docker и окружение

- Приложение в любом окружении — локальном, тестовом и production — должно запускаться через Docker. Поддерживай рабочую конфигурацию контейнеров для frontend, backend и зависимостей; локальный запуск приложения вне Docker не должен быть обязательным шагом.
- Единственный Compose-файл в репозитории — `docker-compose.yaml.example`. Рабочие Compose-файлы создаются отдельно: локальную копию можно менять под себя, production-файл формируется на сервере. Не коммить рабочие Compose-файлы и личные настройки. При изменении состава сервисов или способа запуска обновляй только файл-пример; рабочие конфигурации формируются из него в соответствующем окружении.
- Вместе с приложением через Docker запускаются PostgreSQL, Redis и Keycloak; локально и в тестовом окружении также MinIO с созданием бакета. В production допускается внешний S3-совместимый сервис через `.env`. Определяй сети, тома, готовность зависимостей и порядок запуска так, чтобы система поднималась воспроизводимо без ручного старта этих сервисов.
- Единственный файл переменных окружения во время запуска — `.env`. Единственный допустимый файл с переменными окружения в репозитории — `.env.example`, без настоящих секретов. Не создавай `.env.local`, `.env.production` и другие варианты; не коммить `.env`.
- В `infra/` храни только начальную инфраструктурную настройку PostgreSQL (создание баз и пользователей БД) и Keycloak (realm и роли). Таблицы CRM, их миграции и прикладной seed принадлежат `backend/prisma/`; не изменяй схему CRM скриптами из `infra/`.

## Git и вопросы

- Пиши сообщения коммитов по Conventional Commits: `type(scope): краткое описание` (например, `feat`, `fix`, `docs`, `refactor`, `test`, `chore`). Один логически связанный набор изменений держи в одной рабочей ветке.
- Перед первым push создай собственную ветку от актуальной `development` с названием по типу изменения, например `codex/feat/project-workflow` или `codex/fix/permissions`. Проверь изменения локально и по возможности отправь их одним push; исправления по той же задаче продолжай в этой ветке.
- Перед **каждым** push и **непосредственно перед** созданием MR запускай обязательные тесты и проверки сборки по правилам ниже. Не используй результат проверок, полученный до последних изменений.
- После push создай Merge Request в `development`. На этом действия разработчика по продвижению изменений заканчиваются: не сливай MR самостоятельно и не пушь напрямую в `development`, `staging` или `main`. Продвижение в `staging` и `main` выполняет team lead.
- Если недостающий ответ меняет архитектуру, контракт, безопасность, объём работы или способ реализации, задай пользователю короткий конкретный вопрос. Объединяй связанные вопросы и не останавливай независимую работу; мелкие обратимые решения принимай самостоятельно и явно фиксируй допущения.

## Проверка результата

- Добавляй тесты там, где они проверяют значимое поведение: бизнес-правила, переходы состояния, права, интеграции и критические пользовательские сценарии. Не пиши тесты, которые лишь повторяют реализацию.
- Перед каждым push и созданием MR запускай **все обычные тесты проекта для любых изменений**, включая документацию. Успешный запуск обязателен; отсутствие тестового набора или невозможность его запустить не считается прохождением.
- Перед каждым push и созданием MR запускай проверки сборки приложения и Docker-образов. Пропустить **только проверки сборки** можно, если изменения объективно не способны повлиять на её результат; зафиксируй причину пропуска. Если есть сомнение, запускай сборку. Обычные тесты при этом не пропускаются.
- Если обязательный тест или проверка сборки не прошли либо не были выполнены, **не делай push и не создавай MR**. Исправь причину и повтори проверки после последнего изменения. Не обходи этот запрет флагами или отключением проверок.
- Перед завершением также запусти применимые проверки форматирования, типов и линтинга. Если какую-либо из них невозможно запустить, укажи причину и остаточный риск.
- При изменении архитектуры обновляй этот файл; при изменении контрактов или порядка запуска обновляй соответствующую документацию вместе с кодом.
